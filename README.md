# Pixora 0.6.1

افزونهٔ فارسی وردپرس برای کاهش حجم تصاویر، ساختهٔ **tahanoa**. نسخهٔ ۰.۵.۰ یک موتور مستقل برای **کاهش فضای دیسک با حفظ فرمت و آدرس** اضافه می‌کند؛ این موتور به قواعد هاست، CDN، درخواست HTTP، exec یا کلید API وابسته نیست.

## چه چیزی در روش حل مسئله تغییر کرد؟

[بررسی کد و مستندات WebP Express، Imagify، Modern Image Formats و EWWW](docs/RESEARCH.md) نشان داد تبدیل WebP و کاهش فضای محلی دو مسئلهٔ مستقل‌اند. یک وب‌سرور جلویی مثل Nginx ممکن است فایل اصلی را مستقیماً تحویل دهد و قواعد Apache اجرا نشوند. برای چنین وضعیتی، حذف JPEG/PNG و حفظ همهٔ URLهای قدیمی نیازمند پشتیبانی مسیر تحویل است.

در روش پیشنهادی جدید، JPEG همان JPEG و PNG همان PNG باقی می‌ماند. نسخهٔ کوچک‌تر با همان نام و مسیر جای نسخهٔ بزرگ قبلی می‌نشیند؛ فایل اضافی یا بکاپ دائمی روی هاست ساخته نمی‌شود. **این روش WebP جدید تولید نمی‌کند.** روش WebP قبلی نیز جداگانه در دسترس است و برای حذف اصل همچنان به بررسی موفق هدایت نیاز دارد.

## نصب و استفادهٔ پیشنهادی روی هاست شما

1. قبل از جایگزینی غیرقابل‌بازگردانی، از دیتابیس و uploads بکاپ مستقل بگیرید.
2. `pixora.zip` را از بخش افزونه‌های وردپرس بارگذاری و نسخهٔ قبلی را به‌روزرسانی کنید.
3. وارد منوی **Pixora** شوید و تأیید داشتن بکاپ را علامت بزنید.
4. **«کاهش فضای دیسک با حفظ فرمت و آدرس»** را بزنید؛ دکمهٔ WebP را برای این حالت انتخاب نکنید.
5. گزارش عملیات، میزان کاهش فایل‌ها و آمار «فضای آزادشده با حفظ فرمت» را ببینید.

این کنترل برای هر تصویر در کتابخانهٔ رسانه نیز وجود دارد. اگر فایل جدید کوچک‌تر نشود، هیچ جایگزینی انجام نمی‌شود و «بدون تغییر» گزارش می‌شود. تصاویر از قبل فشرده ممکن است کاهش زیادی نداشته باشند؛ ۹۰٪ تضمین نیست.

برای آپلودهای آینده، در تنظیمات روش **«کاهش دیسک با همان فرمت و آدرس»** را انتخاب و تأیید بکاپ و پردازش خودکار را فعال و ذخیره کنید. تنظیمات قدیمی خودکار به‌صورت پنهانی به این روش غیرقابل‌بازگردانی تغییر داده نمی‌شوند؛ انتخاب و تأیید شما لازم است.

## رفتار موتور هم‌فرمت

- JPEG/PNG، اندازه‌های وردپرس و در صورت امکان `original_image` پردازش می‌شوند؛ شناسه، مسیر، URL و MIME ثابت می‌مانند.
- فایل موقت در همان پوشه ساخته، نوع و ابعاد و اندازه بررسی و فقط در صورت کوچک‌تر بودن با rename اتمی لینوکس جایگزین می‌شود. فایل موقت پس از پایان پاک می‌شود.
- نسخهٔ بزرگ قبلی نگهداری نمی‌شود؛ پس از جایگزینی، کیفیت قبلی فقط از بکاپ مستقل قابل بازیابی است.
- برای جلوگیری از افت کیفیت تکراری، فایل دارای همان هشِ خروجی دوباره بازفشرده نمی‌شود. تغییر کیفیت روی فایل‌هایی که قبلاً با این روش پردازش شده‌اند اثر ندارد مگر خود فایل تغییر کرده باشد.
- PNG متحرک، GIF، SVG، WebP از پیش موجود و JPEG دارای جهت EXIF غیرعادی بدون دست‌کاری باقی می‌مانند. فایل‌های فقط‌خواندنی یا خارج از uploads جایگزین نمی‌شوند. تصاویر بزرگ‌تر از ظرفیت حافظه با گزارش رد می‌شوند.
- اگر تصویر قبلاً به WebP تبدیل شده باشد، JPEG/PNG باقی‌مانده نیز می‌تواند کوچک‌تر شود. WebPهای موجود حذف نمی‌شوند چون ممکن است در محتوای منتشرشده استفاده شده باشند. **این کار پاک‌سازی کامل همهٔ کپی‌های قبلی نیست**؛ آمار جدید فقط کاهش واقعی اندازهٔ فایل‌های جایگزین‌شده را نشان می‌دهد.
- تغییرات کیفیت/رنگ وابسته به ویرایشگر تصویر وردپرس است؛ حفظ پیکسل‌ها برای همهٔ تصاویر تضمین نمی‌شود. آزمون PNG شفافِ این پروژه حفظ دقیق پیکسل‌های همان نمونه را تأیید کرده است.

## روش WebP

تبدیل خودکار یا دستی JPEG/PNG به WebP، پردازش دسته‌ای، حفظ فایل‌های قبلی و بازگشت به فرمت قبلی همچنان وجود دارد. ساخت WebP به‌تنهایی فضای دیسک را بیشتر می‌کند. حذف اصل با WebP فقط پس از تأیید پاسخ نهایی ۲۰۰، MIME برابر WebP و هش دقیق فایل هدف انجام می‌شود. بررسی اولیه پیش از تبدیلِ حالت آزادسازی اجرا می‌شود و شکست مسیر در عملیات هوشمند باعث اجرای روش هم‌فرمت می‌شود؛ رشد خالص دیسک یا خطای خارج از مسیر جایگزین می‌تواند پردازش را متوقف کند.

قواعد هدایت در `.htaccess` پوشهٔ تصاویر باقی می‌مانند و به فعال بودن افزونه وابسته نیستند. هنگام مهاجرت باید منتقل یا با تنظیم معادل وب‌سرور جایگزین شوند. Nginx جلویی ممکن است این قواعد را نادیده بگیرد؛ در آن وضعیت از موتور هم‌فرمت استفاده کنید یا تنظیم وب‌سرور را از پشتیبانی هاست بخواهید.

حذف خودکار پس از تبدیل WebP، با تأیید جداگانه از طریق زمان‌بندی وردپرس انجام می‌شود. خاموش‌کردن آن جلوی کارهای در انتظار را می‌گیرد. زمان اجرای Cron به هاست و بازدید سایت وابسته است. روش هم‌فرمت به این کار زمان‌بندی وابسته نیست.

## پیش‌نیاز و محدودیت

وردپرس 6.5+، PHP 7.4+ و GD یا Imagick لازم است؛ فقط برای روش WebP پشتیبانی نوشتن WebP هم لازم است. فایل‌ها باید روی فایل‌سیستم محلی لینوکس و قابل نوشتن باشند. ذخیره‌سازی خارجی رسانه، سایر بهینه‌سازها و CDN نیازمند آزمون سازگاری‌اند. در CDN ممکن است تا پاک‌سازی کش، نسخهٔ کش‌شدهٔ قبلی دیده شود؛ کاهش دیسک روی فایل‌های هاست اتفاق می‌افتد.

کنترل تکیِ مخرب و عملیات گروهی به مدیر محدودند. درخواست‌ها nonce، مجوز آپلود و ویرایش همان پیوست را بررسی می‌کنند. توقف پس از تصویر جاری، ادامه، شروع دوباره و کپی گزارش پشتیبانی موجود است. محدودیت حافظه/زمان هاست برداشته نمی‌شود؛ خطای مهلک یا کشتن فرایند ممکن است هنوز نیازمند بررسی error_log باشد. منطق قفل فایل و ثبت وضعیت، جلوی پردازش هم‌زمان و بازفشرده‌سازی تکراری را می‌گیرد.

## اعتبارسنجی

```sh
php tests/workflow.php
php tests/storage.php
php tests/fatal-fixture.php
node tests/admin.js
```

آزمون‌های اول از شبیه‌ساز API وردپرس استفاده می‌کنند. آزمون‌های واقعی در یک نصب **یک‌بارمصرف** وردپرس انجام می‌شوند و نباید روی سایت واقعی اجرا شوند:

```sh
docker compose -f tests/compose.yaml up -d --wait
docker compose -f tests/compose.yaml exec -T --user www-data wordpress php /opt/pixora-tests/integration.php --install
docker compose -f tests/compose.yaml exec -T --user www-data wordpress php /opt/pixora-tests/integration.php
docker compose -f tests/compose.yaml exec -T --user www-data wordpress php /opt/pixora-tests/integration-inplace.php
docker compose -f tests/compose.yaml down -v
```

محیط واقعی: WordPress 7.1.4، PHP 8.2.35، MariaDB، Apache برای PHP و **Nginx استاتیک که htaccess را نادیده می‌گیرد**. فایل JPEG آزمایشی از ۱۹۲٬۷۱۴ به ۵۳٬۲۳۴ و PNG آزمایشی از ۱٬۳۹۷٬۱۶۵ به ۵۳٬۱۸۵ بایت رسید؛ این اعداد شامل اندازه‌های وردپرس‌اند و نمونه‌ها از ابتدا قابل فشرده‌سازی بوده‌اند. آدرس‌های قبلی، شفافیت PNG همان نمونه، آمار واقعی، کلیک تکراری، خطای ثبت متادیتا، فایل فقط‌خواندنی و کنترل دسترسی بررسی شدند. نسخهٔ نصب‌شده روی هاست کاربر هنوز مستقلاً آزموده نشده است.

مجوز GPL-2.0-or-later؛ متن در `pixora/LICENSE`.


## گالری و تکراری‌ها — نسخهٔ ۰.۶.۰

از **Pixora ← گالری تصاویر**، تصاویر را با عنوان، فرمت، حجم فایل جاری، تعداد و مجموع حجم فایل‌های قابل ردیابی آن پیوست ببینید. اندازه‌های خودکار وردپرس و اصل/WebP متعلق به یک پیوست، یک رکورد گالری‌اند و تکرار سهوی شمرده نمی‌شوند. این شمارش اسکن کامل uploads برای فایل‌های یتیم نیست؛ نسخه‌های قدیمی بدون اطلاعات ردیابی ممکن است در آن نیایند.

«بررسی یا ادامهٔ بررسی تصاویر» هر بار یک پیوست را نمایه می‌کند و پس از پایان باید صفحه را تازه کنید. توقف، ادامه در همان تب و شروع دوباره موجود است. سه نتیجه جدا هستند:

- **فایل کاملاً یکسان:** SHA-256 فایل؛ نام و پسوند ملاک نیست.
- **پیکسل یکسان:** هش RGBA رمزگشایی‌شده با ابعاد یکسان؛ JPEG، PNG و WebP می‌توانند با پسوند متفاوت در این گروه قرار گیرند. برای تصاویر تا ۲ میلیون پیکسل و دارای حافظهٔ کافی انجام می‌شود.
- **مشابه احتمالی:** dHash به‌همراه کنترل نسبت ابعاد و میانگین رنگ؛ تصویر با فشرده‌سازی با اتلاف یا تغییر اندازه ممکن است در این گروه بیاید. این تشخیص قطعی نیست و برای حذف خودکار استفاده نمی‌شود.

تکرار دقیق در کل نمایه جست‌وجو می‌شود، نه فقط صفحهٔ فعلی. گروه‌های دقیق صفحه‌بندی شده‌اند و هر گروه حداکثر ۲۰ نمونه نمایش می‌دهد. شباهت احتمالی برای ۲۰ مبدأ در هر صفحه، در کل نمایه نامزد می‌گیرد و تا ۱۰۰ نامزد هر مبدأ را بررسی می‌کند؛ نتیجهٔ آن یک فهرست کمکیِ محدود است، نه تضمین یافتن همهٔ شباهت‌ها. GD برای هش پیکسلی و شباهت لازم است؛ بدون آن فقط تطابق فایل انجام و محدودیت گزارش می‌شود. GIF و PNG/WebP متحرک و JPEG دارای جهت EXIF غیرعادی فقط از نظر بایت فایل مقایسه می‌شوند.

به‌روزرسانی فایل یا متادیتا از API وردپرس، نمایهٔ همان پیوست را باطل می‌کند. بعد از تغییر دستی فایل‌ها با FTP نیز بررسی را از ابتدا اجرا کنید. گروه‌ها وضعیت آخرین اسکن را نشان می‌دهند. هیچ فایل تکراری به‌طور خودکار حذف یا جایگزین نمی‌شود؛ استفاده از تصویر در صفحه‌سازها، CSS و لینک‌های خارجی از روی متادیتای وردپرس به‌طور کامل قابل تشخیص نیست.

بالای پنل اصلی، وضعیت واقعی پردازش خودکار آپلود و روش انتخاب‌شده دیده می‌شود. در موتور حفظ فرمت، فایل کوچک‌تر ابتدا ساخته، نوع/ابعاد/اندازه بررسی و سپس با rename اتمی جایگزین می‌شود؛ فایل موقت باقی نمی‌ماند. در حالت WebP با حفظ اصل، دو نسخهٔ دائمی وجود دارد و اندازه‌های بندانگشتی وردپرس نیز جدا هستند.

آزمون واقعی گالری: `php /opt/pixora-tests/integration-gallery.php` در همان محیط Docker یک‌بارمصرف بالا. برای پیش‌نمایش مرورگر، متغیر `PIXORA_GALLERY_EXPORT=/tmp/gallery.html` را فقط روی این آزمون تنظیم کنید، خروجی را از کانتینر بیرون بیاورید و `node tests/gallery-browser.js /path/to/gallery.html` را اجرا کنید. آزمون Chromium از HTML واقعی وردپرس و تصاویر آزمایشیِ درون‌خطی استفاده می‌کند؛ تعامل دکمهٔ اسکن در مرورگر شبیه‌سازی و کنترل دسترسی/AJAX جداگانه با وردپرس واقعی آزموده می‌شوند.

## نسخهٔ ۰.۶.۱ — رفع بن‌بست آزادسازی با روش جایگزین خودکار

دکمهٔ «آزادسازی هوشمند فضا» برای تصاویر دارای WebP و عملیات گروهی «فشرده‌سازی و آزادسازی هوشمند»، پس از شکست بررسی هدایت، روش هم‌فرمت را خودکار اجرا می‌کنند. لازم نیست کاربر پس از دیدن خطای WebP روش دیگری انتخاب کند. این رفتار به‌معنی تضمین حذف پسوند JPEG/PNG نیست: نسخهٔ بزرگ قبلی در صورت وجود نسخهٔ کوچک‌تر، در همان مسیر جایگزین می‌شود و URL سالم می‌ماند. WebPهای منتشرشده حفظ می‌شوند.

آپلود با گزینهٔ آزادسازی خودکار نیز پس از شکست بررسی اولیه، هم‌فرمت بهینه می‌شود و WebP جدید نمی‌سازد. این گزینه همچنان به فعال‌کردن پردازش خودکار و تأیید بکاپ مستقل نیاز دارد. خاموش بودن این گزینه یعنی رفتار انتخاب‌شدهٔ «WebP با حفظ اصل» تغییر نمی‌کند.

گزارش عملیات هوشمند **اختلاف مجموع اندازهٔ فایل‌های قابل ردیابی قبل و بعد از همان درخواست** را به‌عنوان کاهش خالص نشان می‌دهد. حجم WebP تازه‌ساخته‌شده از صرفه‌جویی کم می‌شود. خروجی صفر موفقیت کاذب ندارد؛ اگر هیچ خروجی کوچک‌تری پیدا نشود، صفر بایت و بدون تغییر گزارش می‌شود. رشد خالص، خطا گزارش و پردازش متوقف می‌شود. آمار تاریخی حجم فایل‌های حذف‌شده در روش WebP از کاهش خالص همان عملیات جداست.

در آزمون واقعی، وردپرس PHP پشت Nginx استاتیک قرار گرفت؛ URLهای قدیمی دقیقاً HTTP 200 با MIME برابر JPEG/PNG برگرداندند و همان دکمهٔ آزادسازی به هم‌فرمت تغییر روش داد. پاسخ AJAX با اختلاف مستقل اندازه‌های فایل‌ها تطبیق داشت، درخواست تکراری صفر گزارش داد، فایل‌های WebP قبلی و URLها سالم ماندند و آپلود خودکار هم به روش جایگزین رفت. این تست تأیید محلیِ شرایط گزارش‌شده است و جای تأیید روی هاست کاربر را نمی‌گیرد. PNG از قبل بهینه یا تصویر خارج از ظرفیت حافظه الزاماً کاهش نخواهد داشت.
