# Pixora 0.4.0

افزونهٔ فارسی وردپرس برای تبدیل JPEG و PNG به WebP و آزادسازی اختیاری فضای دیسک، ساختهٔ **tahanoa**.

## نصب و پیش‌نیازها

فایل `pixora.zip` را از بخش افزونه‌های وردپرس بارگذاری و فعال کنید. منوی مستقل **Pixora** در مدیریت ظاهر می‌شود. وردپرس 6.5 به بالا، PHP 7.4 به بالا و GD یا Imagick دارای قابلیت نوشتن WebP لازم است.

تبدیل تصاویر روی سرور انجام می‌شود و نیاز به کلید API ندارد. حذف اصل با هدایت خودکار آدرس‌ها فقط روی Apache یا LiteSpeed و پس از آزمایش واقعی همان هاست در دسترس است. روی Nginx یا هاست ناشناخته، اصل تصاویر حفظ می‌شوند.

## فشرده‌سازی و حذف در یک مرحله

1. از دیتابیس و uploads یک بکاپ مستقل تهیه کنید.
2. در Pixora، تأیید داشتن بکاپ را علامت بزنید.
3. «فشرده‌سازی و حذف اصل در یک مرحله» را انتخاب کنید.

تصاویر JPEG و PNG جدید تبدیل می‌شوند؛ برای تصاویری که قبلاً WebP دارند، تبدیل تکرار نمی‌شود. برای هر پیوست، آدرس اصلی و اندازه‌های مختلف آن باید واقعاً فایل WebP صحیح را برگردانند. فقط پس از تأیید همهٔ آدرس‌های همان پیوست، اصل فایل‌ها حذف می‌شود. شکست بررسی باعث حفظ اصل تصاویر می‌شود. **پس از حذف، بازگردانی از داخل افزونه ممکن نیست؛ بکاپ مستقل لازم است.**

در حالت «فشرده‌سازی تصاویر با Pixora» به‌تنهایی، اصل فایل حفظ می‌شود. کاهش حجم دانلود و فضای آزادشدهٔ دیسک دو آمار متفاوت‌اند. در صورت باقی‌ماندن بخشی از فایل‌ها، تعداد آن‌ها نمایش داده می‌شود و برای ادامهٔ حذف نیاز به بررسی پشتیبانی هاست است.

## کنترل تکی از کتابخانهٔ رسانه

در نمای فهرستی و بخش جزئیات تصویر در نمای شبکه‌ای، وضعیت هر تصویر نمایش داده می‌شود: WebP آماده، اصل موجود، وضعیت انتظار حذف خودکار یا فضای واقعاً آزادشده. مدیر می‌تواند با همان کنترل‌ها تصویر را فشرده و اصل را حذف کند، فقط اصل یک تصویر بهینه‌شده را آزاد کند، یا پیش از حذف به اصل بازگردد. عملیات غیرقابل‌بازگردانی تأیید جداگانه دارد.

فشرده‌سازی تکی نیازمند مجوز آپلود و ویرایش همان رسانه است؛ حذف و بازگردانی از کنترل تکی به مدیر محدود است. درخواست‌ها nonce و کنترل دسترسی سمت سرور دارند.

## آپلودهای آینده و کیفیت

فشرده‌سازی خودکار هنگام آپلود، پیش‌فرض فعال است. کیفیت پیش‌فرض 82 است؛ انتخاب‌های آمادهٔ 70، 82 و 92 یا عدد دلخواه 1 تا 100 وجود دارد. تغییر کیفیت فقط بر تبدیل‌های بعدی اثر دارد.

برای **حذف خودکار پس از آپلود**، فشرده‌سازی خودکار و آزادسازی خودکار را فعال کنید و تأیید بکاپ را بزنید و تنظیمات را ذخیره کنید. پس از تبدیل موفق، یک کار زمان‌بندی وردپرس برای بررسی آدرس‌ها و آزادسازی ثبت می‌شود؛ حذف داخل درخواست آپلود انجام نمی‌شود. زمان‌بندی معمولاً با بازدید سایت اجرا می‌شود، بنابراین زمان دقیق حذف تضمین‌شده نیست. اگر زمان‌بندی وردپرس روی هاست اجرا نشود، عملیات در انتظار می‌ماند و کنترل دستی در دسترس است. خاموش‌کردن آزادسازی خودکار جلوی حذف توسط کارهای در انتظار را می‌گیرد. خطای بررسی به حذف خودکارِ بی‌پایان یا تکرارشونده منجر نمی‌شود؛ وضعیت آن در رسانه نمایش داده می‌شود.

## ادامه و گزارش خطا

پردازش هر پیوست در یک درخواست انجام می‌شود. توقف پس از تصویر جاری، ادامه از آخرین شناسهٔ تأییدشده، شروع دوباره از ابتدا و کپی گزارش پشتیبانی در پنل وجود دارند. نتیجه‌ها شامل موفق، بدون تغییر، ناموفق و «WebP آماده، اصل محفوظ» هستند. برای موارد ردشده، شروع دوباره از ابتدا را بزنید.

پیشرفت هر نوع عملیات در همان تب مرورگر ذخیره می‌شود. خطاهای HTTP و خطاهای قابل‌گرفتن PHP گزارش می‌شوند. برای خطاهای مهلک PHP، شناسه و مرحله به‌صورت best effort بازگردانده می‌شود؛ کشتن فرایند توسط وب‌سرور یا سیستم‌عامل ممکن است همچنان نیازمند error_log هاست باشد. محدودیت زمان/حافظهٔ هاست با نصب افزونه حذف نمی‌شود. قفل‌های جدید با پایان فرایند آزاد می‌شوند؛ قفل دیتابیس نسخه‌های قدیمی تا یک ساعت برای جلوگیری از تداخل حفظ و پس از آن کنار گذاشته می‌شود.

## حفظ لینک‌ها و محدودیت‌ها

- قواعد آدرس‌های قدیمی در `.htaccess` همان پوشهٔ تصاویر ثبت می‌شوند و پس از غیرفعال‌کردن افزونه باقی می‌مانند. هنگام مهاجرت، فایل‌های مخفی را هم منتقل کنید. حذف قواعد یا مهاجرت به Nginx بدون تنظیم معادل می‌تواند لینک‌های قدیمی را خراب کند.
- هدایت حداکثر سه‌مرحله‌ای فقط به hostnameهای ثبت‌شدهٔ وردپرس، سایت و uploads پذیرفته می‌شود. پاسخ نهایی باید 200، نوع محتوا WebP و هش محتوا دقیقاً برابر فایل هدف باشد. TLS غیرفعال نمی‌شود.
- JPEG، PNG شفاف، اندازه‌های وردپرس و در تبدیل‌های جدید، `original_image` وردپرس پوشش داده می‌شوند. برای رسانه‌های بهینه‌شده با نسخه‌های قدیمی، فایل‌های فاقد نگاشت حذف نمی‌شوند. پیش از حذف می‌توان آن‌ها را بازگرداند و دوباره بهینه کرد تا نگاشت کامل جدید ساخته شود.
- PNG متحرک، GIF، SVG و WebP از پیش موجود تبدیل نمی‌شوند. ذخیره‌سازی خارجی رسانه، CDN، بازتولید اندازه‌ها توسط افزونه‌های دیگر و سایر بهینه‌سازها نیازمند آزمون سازگاری‌اند.
- فایل‌های دارای نویسه‌های ویژهٔ نامناسب برای قواعد هدایت یا خروجی بالای 20 مگابایت خودکار حذف نمی‌شوند. نام فارسی در نسخهٔ 0.4.0 پشتیبانی می‌شود.
- کاهش حجم 90٪ یا حفظ دقیق کیفیت تضمین نمی‌شود؛ تبدیل با اتلاف است. فقط مجموعهٔ خروجیِ کوچک‌تر جایگزین می‌شود. تا پیش از حذف اصل، فضای دیسک بیشتر مصرف می‌شود. WebPهای ساخته‌شده پس از بازگردانی نیز برای حفظ لینک‌های منتشرشده نگهداری می‌شوند.

## اعتبارسنجی توسعه

```sh
php -l pixora/pixora.php
php tests/workflow.php
php tests/storage.php
php tests/fatal-fixture.php
node tests/admin.js
```

آزمون‌های workflow و storage از شبیه‌ساز API وردپرس استفاده می‌کنند. fatal-fixture عمداً یک خطای مهلک در فرایند جدا تولید و پاسخ تشخیصی را بررسی می‌کند.

`tests/integration.php` آزمون **وردپرس واقعی و مخرب برای داده‌های آزمایشی** است؛ فقط در نصب یک‌بارمصرف داخل کانتینر اجرا شود. نسخهٔ 0.4.0 با WordPress 7.1.4، PHP 8.2.35، MariaDB و Apache آزمایش شده است: JPEG، PNG شفاف، srcset، بازگردانی، حذف هم‌زمان، نسخهٔ بزرگ اولیه، آدرس‌های قدیمی، زمان‌بندی، دسترسی نقش‌ها، nonce و غیرفعال‌سازی. نتیجهٔ این آزمون به معنی تأیید همهٔ هاست‌ها یا LiteSpeed نیست؛ افزونه بررسی آدرس‌ها را روی هاست مقصد تکرار می‌کند.

مجوز: GPL-2.0-or-later؛ متن در `pixora/LICENSE`.

اجرای تکرارپذیر آزمون واقعی با Docker Compose (فقط محیط تست بدون پورت منتشرشده؛ دیتابیس عمداً یک‌بارمصرف است):

```sh
docker compose -f tests/compose.yaml up -d --wait
docker compose -f tests/compose.yaml exec -T --user www-data wordpress php /opt/pixora-tests/integration.php --install
docker compose -f tests/compose.yaml exec -T --user www-data wordpress php /opt/pixora-tests/integration.php
docker compose -f tests/compose.yaml down -v
```

در محیط‌های دارای پراکسی، تنظیم پراکسی و CA معتبر Docker را حفظ کنید؛ این آزمون پس از دریافت تصاویر، فقط از شبکهٔ داخلی و localhost استفاده می‌کند.
